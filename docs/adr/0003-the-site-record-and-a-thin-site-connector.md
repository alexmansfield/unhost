# The Site record is platform-agnostic and the site connector contract is thin

A **Site** is identified on the wire by a `slug` — the `site` argument every gateway tool takes — with the database `id` never leaving the database. It carries a `domain` (the public address, not the connector's endpoint), a nullable, mutable `platform` key, and exactly one stored status input, `paused_at`; every other status is derived per actor at read time. A platform integration reaches a site by implementing `SiteConnector` — `label()`, `refuse(actor, site)`, `panel()` — offered into the `sites` registry under the platform key, and **the credential never leaves the integration**: the gateway defines its own proxy contract, which the same integration implements separately.

## Decisions folded in

- **Identity is a slug; the `id` is internal.** Kebab-case, unique per tenant, derived from the name on create and editable by staff, because `example-site` is what an operator says and a model types. A ULID was rejected as unmemorable in tool output, and the domain as identity because a site that moves host would change identity for a DNS reason. The `id` stays a bigint that never appears in a URL, an API response or tool output, which is what makes it safe for feature modules to key on.
- **`domain`, not `url` or `host`.** The scheme is dropped: every outbound path forces `https` (WordPress refuses to issue application passwords on a non-HTTPS site; authwp's guarded fetch is https-only), so a stored scheme carries no information and can lie. `host` was rejected for colliding with Dashbird's `Host` — the company that hosts a site — and with the later `hosting` module. The value is lowercased and otherwise stored as entered, with no `www.` stripping, since a site genuinely served at `www.` gets a redirect on every link if stripped. Dashbird's actual mistake was narrower than "it normalised": it was a column **named `url`** that held a bare host, so every reader had to know the name was wrong.
- **`domain` is the public address, never promised to be the connector's endpoint.** For WordPress they are the same string; for a platform whose coordinates are an account and project id they are unrelated. A subdirectory or headless WordPress install's REST base override lives in `wordpress`, and a port for a local Cove site is likewise the connector's business — a domain name holds no port.
- **`platform` is nullable and mutable.** It was to be "set at onboarding and never edited"; that cannot hold, because a site moving from Squarespace to WordPress is ordinary and immutability would force deleting the site, losing its slug, client, assignments and every feature module's history for a CMS change. Platform is therefore a current fact, not identity — and once mutable, null is simply the value before the fact is known. Null also admits the site unhost **monitors but cannot reach into**, which `dns` and `uptime` make a real case rather than a hypothetical. A sentinel (`unknown`, `none`) was rejected as a nullable column in a costume that the connector registry might try to resolve. Deriving platform from a credential's existence was rejected for collapsing "a WordPress site whose credential is revoked" into "not a WordPress site", which the status precedence depends on keeping apart.
- **Changing platform does not reach into the old integration's table.** `sites` does not know `wordpress` exists and there is no cross-module foreign key; the old credential row goes inert, because a connector is consulted only when `platform` matches its key. Staff remove it explicitly. The lingering stale credential is a known, inert hazard and the `wordpress` ticket's to handle.
- **One stored status input, `paused_at`; everything else derived per actor.** A nullable timestamp in core's `disabled_at` idiom, answering "since when" for free. With no sync in this slice, `paused` means **the gateway refuses this site** — a kill switch for a site mid-migration, under attack, or whose client access is suspended. Precedence: `paused_at` set → paused; else no platform or no active connector → not reachable; else ask the connector for this actor. `sites` owns that enum; the connector's refusal sentence rides beside it as an uninterpreted `detail`, so Dashbird's `limited` (a credential lacking `activate_plugins`) can map onto the open/dangerous split without `sites` knowing what that is.
- **Status is per (actor, site), not per site**, because credentials are per user per site. A per-site aggregate — "connected if any credential works" — was rejected for telling a client their site is fine when their own credential is the broken one, which is the support call it exists to prevent. The consequence is that a staff member debugging a client's complaint must be able to see the *client's* view on the site detail page.
- **The connector answers from stored state and never probes.** The spike measured ≈ 1 s per round trip to a live site, so `list-sites` over a hundred sites cannot probe. A probe is an explicit act — onboarding, a "test connection" button, a later scheduled refresh — writing its outcome to the integration's own row.
- **The credential never leaves the integration**, against the discovery record's D3, which had the contract resolve one for `(actor, site)`. Three reasons: the gateway would otherwise have to know Basic auth, REST base derivation and authwp's `authwp_` token shape, all integration business; the research found that serialising a laravel/mcp client writes the credential in plaintext, so a credential travelling through gateway code is one refactor from a queue payload; and D3's own rule says credentials belong to integrations, not features — and the gateway is a feature.
- **Two contracts for one integration, not one fat one.** `wordpress` implements `SiteConnector` (from `sites`) and the gateway's proxy contract (ticket #13's), offering into both registries from one `bootModule()` behind `class_exists`. Merging them into a `sites`-owned interface would force `sites` to declare tool-calling methods it never calls, and switching the gateway off would leave the pass-through present but unused rather than genuinely gone — losing the property D3 wanted on exactly that surface. This is Dashbird's integration manifest pattern (one Cloudflare token serving `dns` and `hosting`) as a PHP interface. A platform with no MCP endpoint implements `SiteConnector` alone and is simply not proxyable, which is a real state rather than an unimplementable method.
- **`panel()` on the connector rather than a site-detail panel registry.** `sites` cannot render WordPress's credential block — it does not know what an application password is, and naming `wordpress` would invert the dependency — so the connector returns a Livewire component name the page renders blindly. A site has exactly one platform and therefore exactly one such panel, so there is no ordering, hiding or replacement to implement. A real registry is **deferred, not rejected**: it would be the fifth and sixth hand-written copies of the behaviour Scatterblend #79 exists to consolidate, and the moment to build it is when the gateway wants site-context UI (ticket #13 or #16), by which time #79 may have given core a base to extend.
- **Client stays in `sites`; being a top-level nav item is not an argument for being a module.** The sidebar is a contribution and nothing in it reveals which package an item came from; module boundaries are activation boundaries. A `clients` module fails that test — it could never be switched off without taking every site's ownership and the whole access model with it — and splitting would turn `client_id` from a foreign key into an unconstrained id, put `Access::of()`, the most-executed query in the system, across a module boundary, and move the doubling rather than remove it (`clients:clients:manage`). If billing, contacts or a CRM surface ever appears, `clients` becomes its own module and `sites` keeps an unconstrained `client_id`; until then the extraction seam is marked, as ADR 0001 did for elevation.
- **Five capabilities, no tiers.** `sites:sites:view` is new, held by all three roles, gating the Sites area and `list-sites`; ADR 0002's four manage capabilities are unchanged. The MCP module's convention forces the choice — a tool declares a capability or is explicitly marked open, never both — and marking it open was rejected because a capability is the unit an OAuth token scope can narrow to, so "a read-only agent connection" is expressible only if the name exists. It grants nobody anything in v1 and is the weakest of the five, but adding it later would mean revisiting the role set. The doubling in `sites:sites:*` is unavoidable and mostly invisible: the module owns four nouns (sites, clients, attachments, assignments) and only one of them repeats the key. `key:verb` is not available — segment count is how the role-set validator tells a core capability from a module's, and it is what lets an inactive module's capability resolve to nothing rather than erroring.

## Consequences

- `sites_sites`: `id`, `tenant_id`, `slug` (unique per tenant), `name`, `domain`, `platform` (nullable), `client_id` (nullable, in-module), `paused_at` (nullable), timestamps. No credential columns, no feature remote-ids, no stored connection status — all three of Dashbird's mistakes left behind.
- `Site::scopeVisibleTo(User $actor)` and `Access::of(User $actor, Site $site): ?Access` are the two pieces of machinery `SitePolicy` calls, and `sites` publishes them along with the `Site` model to any module declaring `$requires = ['sites']`. A type dependency across modules is allowed; only the foreign key is not.
- `list-sites` returns one line per site with five fields — `site` (the slug), `name`, `domain`, `platform`, `status` — plus `detail` only when the status is not connected, and the client's name only for actors who can see more than one client. It is a lookup table from human words to slugs, not a report: every field is multiplied by the fleet and re-sent on every connection, since clients cache the tool catalogue but never results.
- Four pages — Sites list, site detail, add a site (`sites:sites:manage`), Clients list and detail (`sites:clients:manage`) — and two sidebar items, Sites for everyone and Clients for staff. A client manager gets no nav item: their people screen is a settings card beside core's Members card, the same act at a narrower scope, because they hold `sites:attachments:manage` and not core's `members:manage`.
- **The gateway needs a third refusal** beside ADR 0002's `site_not_found` and `insufficient_access`: the site exists, the actor has access, and there is no connector for it. Naming it is ticket #13's.
- A site is **hard-deleted** and fires **`SiteDeleting`** synchronously inside the transaction, in core's `UserDeleting` shape: each feature module listens from `bootModule()` and disposes of its own rows, and a throwing listener aborts the deletion. Without a foreign key there is no cascade, so the event *is* the cleanup mechanism. Soft-deleting was rejected because every feature module would have to remember to exclude trashed sites and `scopeVisibleTo()` would quietly include them.
- Whether the gateway's audit rows should survive their site — nulling `site_id` and keeping a denormalised domain and slug — is left to ticket #16; the event gives it the choice.
- `CONTEXT.md` gains Domain, Registered domain, Platform, Site connector and Slug, and reserves Host for the `hosting` module's later use.
