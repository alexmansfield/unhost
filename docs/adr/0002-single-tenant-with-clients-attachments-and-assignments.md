# One tenant, three roles, and site access through ownership or assignment

unhost runs in Scatterblend's single tenancy mode with one tenant (the studio) and a three-role set — `staff` (founding), `subcontractor`, `client` — declared in the application provider. Who may act on a site is not a permission on the site: **staff** hold every capability and see every site by role alone; a **client** is an organisation record in the `sites` module to which sites *belong* (`client_id`, nullable — studio-owned sites have none) and to which client-role people are *attached* with an access value; a **subcontractor** is *assigned* to individual sites, each assignment carrying its own access. Access is one enum, `view` / `edit` / `manage`, and the derived question "may this actor act on this site, and how deeply" is answered from role, attachment or assignment — never from a null owner matching a null client, which is the leak Dashbird's `users.client_id`/`sites.client_id` join had.

## Considered options

- **Clients as bare users with per-site grant rows** (discovery record D2, the map's original *grant*). Rejected: a site belongs to an organisation, not a person, and access follows ownership — the museum's second login must see the museum's sites without a new row per person per site. The word *grant* is retired; it split into attachment and assignment.
- **Subcontractors as clients with narrower grants.** Rejected on vocabulary alone: a subcontractor is assigned to sites regardless of who owns them, and calling them a client misdescribes the relationship in every screen.
- **Access on the role** (Dashbird's `client_owner` / `editor` / `viewer`). Rejected: the role says what kind of user you are, the attachment or assignment says which sites and how deeply; one client can hold different access on different attachments only if the value lives on the row. Values are verbs (`view`/`edit`/`manage`) rather than `viewer`/`editor`/`admin` because `admin`/`owner` are on Scatterblend's avoid list and verbs match capability vocabulary. *Level* is avoided because Scatterblend's *tier* claims it; *permission* because *capability* does.
- **A separate "client admin" flag** decoupling "manages the client's people" from "deepest site access". Rejected: they are the same person; `manage` access on an attachment makes its holder a client manager.
- **Agent-specific access** (a connection scoped to a subset of sites, or agents holding grants narrower than their owner). Rejected: an agent is a Scatterblend user with a role, attached or assigned exactly as a person is; a person's MCP connection acts as the person. Per-site connection scoping would be a Scatterblend change with no consumer in this slice.
- **Honest `forbidden` when the actor has no access to a named site.** Rejected: it leaks the client list one guess at a time. No access is indistinguishable from no such site (`site_not_found`); access that exists but is too shallow is `insufficient_access`, because there the site is already known and the remedy is a manager, not a slug.

## Consequences

- `sites` owns four capabilities: `sites:sites:manage` (create, edit, remove a site; set or clear its owning client), `sites:clients:manage` (client records, and attachments to any client), `sites:assignments:manage` — all three on `staff` only — and `sites:attachments:manage` on `client`, whose policy limits it to the actor's own client and requires the actor's own access to be `manage`. Client managers invite (the `sites` module calls core's `CreatesInvitations` with the role fixed to `client`, remembering client and access to attach on acceptance), detach and set access within their client. Removing a site from unhost stays staff-only; whether `manage` access is the precondition for unlocking dangerous tools is the elevation ticket's to decide, and this is its hook.
- Removing a membership drops that user's attachment and assignments. Deleting a client clears `client_id` on its sites, which remain visible to staff and to anyone assigned.
- `list-sites` returns only the actor's accessible sites; every gateway tool resolves `site` through the same access check and returns `site_not_found` or `insufficient_access` in `structuredContent.code` (the wire result has no error-code field).
- ADR 0001's mention of `sites_grants` is superseded: the tables are `sites_clients`, `sites_attachments`, `sites_assignments`, all carrying `tenant_id` under `BelongsToTenant`; `client_id` on `sites_sites` is an in-module key.
- Every table carries `tenant_id`, so multi tenancy later (a studio per tenant) is additive and does not reopen this decision.
