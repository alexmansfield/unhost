# WordPress application passwords and roles for the gateway

Research ticket: [#5](https://github.com/alexmansfield/unhost/issues/5). Part of the map, [#1](https://github.com/alexmansfield/unhost/issues/1).

Sources are WordPress core **7.0.1** as checked out at `~/Cove/Sites/example.localhost/public/` (`wp-includes/version.php`: `$wp_version = '7.0.1'`); file paths below are relative to that root and line numbers are for that version. Where the local copy could disagree with upstream, the claim was cross-checked against `WordPress/wordpress-develop` trunk or the Trac changeset. developer.wordpress.org and WP-CLI docs are cited by URL. The RestlessWP plugin (v0.9.11, `wp-content/plugins/restlesswp`) was read only far enough to name the capabilities its permission callbacks check; its tool surface is catalogued in [#3](https://github.com/alexmansfield/unhost/issues/3).

## Answers

1. **Can an app-password-authenticated REST request create, list or delete application passwords?** Yes, for its **own user**, at any role, and it can delete **itself**. Every app-password meta capability (`create_app_password`, `list_app_passwords`, `read_app_password`, `edit_app_password`, `delete_app_passwords`, `delete_app_password`) maps to `edit_user` (`wp-includes/capabilities.php:800-807`), and `edit_user` on your own ID returns an empty requirement list, i.e. always allowed (`capabilities.php:69-72`). Core never distinguishes an app-password session from a cookie session for capability purposes. For **other users** it needs `edit_users` (Administrator on single site; super admin only on multisite). The brief's runbook assumption ("the Gateway cannot revoke itself") is **wrong in the permissive direction**: the gateway *can* revoke its own credential (`DELETE /wp/v2/users/me/application-passwords/{uuid}` after `GET .../introspect` to learn its own UUID), and — the hazard — a leaked credential can also **mint new passwords on the same user** and **change that user's login password and email** via `POST /wp/v2/users/me`.
2. **Limits and tracking.** No per-user cap (the array is just appended, `class-wp-application-passwords.php:111-113`). Names must be non-empty/non-whitespace but need **not** be unique since WordPress 6.7 (r59084, Trac #54213; the 5.7 uniqueness check was removed and `application_name_exists_for_user()` has no remaining caller). No scoping, no expiry: the record is `uuid, app_id, name, password (hash), created, last_used, last_ip` and nothing else. `last_used`/`last_ip` are updated **at most once per 24 h** per password (`:344-350`), and `last_ip` is `$_SERVER['REMOTE_ADDR']` (the proxy/CDN address if one is in front). `GET /wp/v2/users/me` returns `id`, `name`, `slug`, `url`, `description`, `link`, `avatar_urls`, `meta` by default; you must request **`?context=edit`** to get `username`, `email`, `roles`, `capabilities` (all caps, resolved) and `extra_capabilities` (caps on the user row) — permitted for any authenticated user on itself.
3. **Least privilege.** An **Editor** credential covers all content work the gateway will proxy: posts/pages CRUD including others' content and publishing, media upload/edit/delete, categories/tags, comments moderation, reading the active theme, and every RestlessWP tool whose write cap is `edit_posts`/`edit_others_posts`. **Administrator is forced** for: users (list with `context=edit`, create, delete, role changes, other users' app passwords), plugins (any plugins endpoint, even listing, needs `activate_plugins`), themes list/switch (`switch_themes`), settings (`manage_options`), site health, and all RestlessWP schema/config modules (ACF field groups/post types/taxonomies, Etch styles/components/templates, ACSS, TSF settings, GF via Gravity Forms caps). Author/Contributor/Subscriber are not workable: Author cannot touch pages or others' posts; Contributor cannot publish or upload; Subscriber can only read. Table in §4.
4. **Revocation paths.** (a) Profile page: Users → Profile → Application Passwords → Revoke / Revoke all — this UI itself calls the REST endpoints above. (b) REST: `DELETE /wp/v2/users/{id}/application-passwords` (all) or `/{uuid}` (one). (c) WP-CLI: `wp user application-password delete <user> --all` or `<uuid>…`, `<user>` by login, email or ID. (d) Site-wide kill switch: `add_filter('wp_is_application_passwords_available','__return_false')` refuses authentication without deleting anything. **Not** revocation: changing the user's role (the credential keeps working with the new role's caps, immediately), changing the user's password, destroying sessions, or deactivating any plugin (RestlessWP, authwp or otherwise — app passwords are core user meta with no plugin dependency). Deleting the user deletes the meta and therefore the passwords (single site); on multisite, deleting from one site only removes the blog membership and the credential keeps working on the user's other sites.
5. **Multisite.** App passwords are user meta, so one credential authenticates on **every site in the network** the user belongs to; the "in use" flag is a network option. Only super admins can manage *other* users' passwords, create/delete users, or install/update/delete plugins, themes and core (`capabilities.php:75, 634, 676-677`); a site Administrator's REST plugin activation additionally needs the network's `menu_items['plugins']` setting or `manage_network_plugins`. The controller 404s any user who is not a member of the current site unless they have `manage_sites` (`class-wp-rest-application-passwords-controller.php:722`).

## 1. Storage, format and authentication

**Storage.** All of a user's application passwords live in a single serialised user-meta row, `_application_passwords` (`wp-includes/class-wp-application-passwords.php:24, 455-457`). Each item is `uuid`, `app_id`, `name`, `password` (hash), `created` (Unix time), `last_used`, `last_ip` (`:101-109`). A network-level option `using_application_passwords` is flipped on the first creation and short-circuits the authenticator when false (`:33, 119-122`; `wp-includes/user.php:382-384`).

**Format.** 24 alphanumeric characters from `wp_generate_password(24, false)` (`:42, 98`), returned once in plain text, chunked into groups of four for display (`:467-474`). On authentication all non-alphanumerics are stripped, so the password works with or without spaces (`user.php:449-455`). Hashed with `wp_fast_hash()` (libsodium `crypto_generichash`, `$generic$` prefix) since 6.8; pre-6.8 phpass hashes are still accepted (`:484-514`; `wp-includes/functions.php:9363-9368`).

**Authentication path.** `determine_current_user` → `wp_validate_application_password()` reads `PHP_AUTH_USER`/`PHP_AUTH_PW` (HTTP Basic) and calls `wp_authenticate_application_password()` (`user.php:521-544`; hooked in `wp-includes/default-filters.php:505, 509`). That function only runs for REST and XML-RPC requests (`XMLRPC_REQUEST`/`REST_REQUEST`, filter `application_password_is_api_request`, `user.php:387-402`), so an app password can never log into wp-admin, but it *does* work on `xmlrpc.php`. The username may be a login or an email (`:405-409`). Each stored hash is checked in turn (`:457-462`); a matching one fires `wp_authenticate_application_password_errors` (a plugin veto point), records usage, fires `application_password_did_authenticate` and returns the user (`:478-499`). Failures are surfaced to the REST layer as 401 by `rest_application_password_check_errors` (`wp-includes/rest-api.php:1231-1255`, hooked at `default-filters.php:340`). The authenticated password's UUID is kept in a global and exposed by `rest_get_authenticated_app_password()` (`rest-api.php:1193-1218`).

**Availability.** `wp_is_application_passwords_supported()` is `is_ssl() || 'local' === wp_get_environment_type()` (`user.php:5126-5128`); `wp_is_application_passwords_available()` wraps it in a filter (`:5140-5149`), and `wp_is_application_passwords_available_for_user()` adds a per-user filter defaulting to true (`:5162-5184`). A non-HTTPS production site refuses app-password authentication with `application_passwords_disabled` (`user.php:424-428`) and its REST endpoints return 501 (`class-wp-rest-application-passwords-controller.php:682-688`). The handbook says the same: credentials are "passed along to REST API requests served over https:// using Basic Auth" ([Authentication](https://developer.wordpress.org/rest-api/using-the-rest-api/authentication/)); the integration guide documents the `__return_false`/`__return_true` overrides ([Application Passwords: Integration Guide](https://make.wordpress.org/core/2020/11/05/application-passwords-integration-guide/)).

**Basic-auth plumbing.** Core's 5.6 upgrade regenerates `.htaccess` to add the `HTTP_AUTHORIZATION` rewrite rule (`wp-admin/includes/upgrade.php:2282-2288`, Trac #51723). Sites on nginx/FPM or with a custom `.htaccess` are the usual reason a valid credential 401s.

## 2. The REST endpoints and who may call them

Controller: `wp-includes/rest-api/endpoints/class-wp-rest-application-passwords-controller.php`. Routes (`:34-102`), confirmed by the [REST reference](https://developer.wordpress.org/rest-api/reference/application-passwords/):

| Method | Route | Permission callback → capability checked | Line |
|---|---|---|---|
| GET | `/wp/v2/users/{id\|me}/application-passwords` | `list_app_passwords` on the target user | `:119` |
| POST | same | `create_app_password` | `:216` |
| DELETE | same (deletes **all**) | `delete_app_passwords` | `:373` |
| GET | `.../application-passwords/introspect` | current user must equal target (`get_current_user_id() !== $user->ID` → error) | `:491` |
| GET | `.../application-passwords/{uuid}` | `read_app_password` | `:172` |
| POST/PUT/PATCH | `.../{uuid}` (rename only) | `edit_app_password` | `:299` |
| DELETE | `.../{uuid}` | `delete_app_password` | `:428` |

**Capability resolution.** All six meta caps collapse to `map_meta_cap('edit_user', $user_id, $target_user_id)` (`wp-includes/capabilities.php:800-807`). `edit_user`: a non-existent user gets `do_not_allow`; **the same user editing themself returns with `$caps` empty, which `WP_User::has_cap()` treats as granted**; otherwise on multisite the caller needs `manage_network_users` (and must be a super admin to edit a super admin) else `do_not_allow`, and on single site it maps to `edit_users` (`capabilities.php:61-80`). `edit_users` is granted only to Administrator (`wp-admin/includes/schema.php:764`).

Consequences:

- Any role can list, create, rename and delete **its own** passwords, including the one it is currently authenticating with (there is no self-exclusion in `delete_item`, `:447-474`).
- The `introspect` route lets the gateway learn the UUID of the credential it is holding (`:510-538`), which is the clean way to revoke exactly itself.
- `POST /wp/v2/users/me/application-passwords` with a `name` returns the new plaintext password in the `password` field (`:254-257, 624-626`; schema `:825-830`). The integration guide advertises this as the programmatic path.
- A single-site Administrator credential can do all of the above for **every** user; an Editor credential cannot touch anyone else's.
- The deprecated `do_permissions_check()` (`:549-567`) is the pre-5.7 `edit_user`-only check; the meta caps exist so plugins can filter them individually via `map_meta_cap`, but core grants them identically.

**`/wp/v2/users/me`.** `GET` has `permission_callback => '__return_true'` (`class-wp-rest-users-controller.php:130`) and returns 401 `rest_not_logged_in` if unauthenticated (`:534-542`). Field contexts (`:1400-1525`): `username`, `email`, `first_name`, `last_name`, `locale`, `nickname`, `registered_date`, `roles`, `capabilities`, `extra_capabilities` are **`edit` context only**; `roles` additionally requires `list_users` or `edit_user` on the target, which self always satisfies (`:1096-1098`). So verification is `GET /wp/v2/users/me?context=edit` and reading `id`, `username`, `roles` (e.g. `["editor"]`) and `capabilities` (the resolved `allcaps` map, `:1105-1106`). `POST /wp/v2/users/me` routes through `update_item_permissions_check` with the caller's own ID (`:865-869`); `edit_user` on self passes, and the prepared user accepts `email` and `password` (`:1180-1190`). Changing `roles` on self is blocked from dropping `edit_users` and gated by `promote_user` (`:725-733, 1257-1290`).

## 3. Limits: count, names, tracking, scope, expiry

| Property | Fact | Source |
|---|---|---|
| Passwords per user | Unlimited; `create_new_application_password` appends and saves | `class-wp-application-passwords.php:111-113` |
| Name | Required; `sanitize_text_field`; empty → 400 `application_password_empty_name`; schema `minLength 1`, `pattern .*\S.*` | `:90-96`; controller `:817-824` |
| Name uniqueness | **Not enforced** since WordPress 6.7. r59084 (2024-09-24, "App Passwords: Don't prevent non-unique App Password names", fixes #54213) removed the 5.7 check from r50030; the `@since 5.7.0 Returns WP_Error if application name already exists` docblock is stale and `application_name_exists_for_user()` (`:238-248`) has no caller in core | `git log` of `WordPress/wordpress-develop` ec80646; trunk `class-wp-application-passwords.php` confirmed identical |
| `app_id` | Optional UUID the application supplies "to uniquely identify it"; recommended v5 UUID from URL/DNS namespace; validated as UUID on the authorize flow; not unique per user; not changeable after creation via REST (`prepare_item_for_database` only accepts it when no `uuid` is in the request) | controller `:582-584, 802-816`; `wp-admin/includes/user.php:677-682` |
| Scoping | None. No capability subset, no route allow-list, no site restriction. Extension points: `wp_authenticate_application_password_errors` (veto per password at auth time), `wp_is_application_passwords_available_for_user`, `application_password_is_api_request` | `user.php:466-485, 5175-5183, 389-398` |
| Expiry | None; only `created` is stored. Any rotation policy must be the gateway's | `:101-109` |
| `last_used` / `last_ip` | Set on successful auth but **throttled to once per `DAY_IN_SECONDS`** per password; `last_ip = $_SERVER['REMOTE_ADDR']`; both `null` until first use; exposed as GMT `Y-m-d\TH:i:s` strings in the REST item | `:336-363`; controller `:619-621` |
| Rate limiting / lockout | None in core; each attempt is a fast hash compare per stored password | `user.php:457-462` |
| Which surfaces accept it | REST and XML-RPC only; never cookie/wp-admin | `user.php:386-402` |

WP-CLI mirrors the same store: `wp user application-password create <user> <app-name> [--app-id=…] [--porcelain]`, `list`, `get`, `update`, `delete`, `exists`, `record-usage` ([wp user application-password](https://developer.wordpress.org/cli/commands/user/application-password/)). `--porcelain` prints only the plaintext password, which is what fleet minting scripts would capture; minting as a product feature is out of scope per the map.

**RestlessWP's own checks** (`wp-content/plugins/restlesswp`). Every RestlessWP route and ability is guarded by `RestlessWP_Auth_Handler::permission_callback( $capability )`, which is a plain `current_user_can( $capability )` (`classes/class-auth-handler.php:28-45`); the MCP transport itself only requires `is_user_logged_in()` (`classes/class-mcp-server.php:141-149`), and tool-level checks run at call time. Each controller declares a read and a write capability (`classes/class-base-controller.php:55-62`, used at `:295-334`). Observed values:

- `edit_posts` read / `edit_posts` write, plus `edit_post` per post: ACF post values, ACF options-page values, Etch field values, Etch pages (`modules/class-acf-post-values-controller.php:90-101, 227`; `class-etch-field-values-controller.php:47-52, 341`; `class-etch-pages-controller.php:53-58`; `class-acf-options-page-values-controller.php:106-116`). **Editor-workable.**
- `edit_posts` read / `edit_others_posts` write: TSF post SEO, TSF term SEO (`class-tsf-post-seo-controller.php:38-45`; `class-tsf-term-seo-controller.php:32-39`). **Editor-workable.**
- `edit_posts` read / `edit_users` write: TSF user SEO (`class-tsf-user-seo-controller.php:35-42`). **Administrator to write.**
- `edit_posts` read / `manage_options` write: ACF field groups, post types, taxonomies, options pages; Etch blocks, components, field groups, loops, styles, stylesheets, templates; all guide controllers (`class-acf-field-groups-controller.php:49-58` and siblings; `class-etch-*-controller.php`). **Administrator to write.**
- `manage_options` for both: ACSS classes/variables/CSS variables, TSF settings, TSF post-type-archive SEO, ACF field CRUD, Etch module routes and editor lock (`class-acss-*.php`; `class-tsf-settings-controller.php:35-42`; `trait-acf-field-crud.php:78`; `class-etch-module.php:131`; `class-etch-editor-lock.php:52`). **Administrator.**
- Gravity Forms module: Gravity Forms' own caps `gravityforms_edit_forms`, `gravityforms_delete_forms`, `gravityforms_view_entries`, `gravityforms_edit_entries`, `gravityforms_delete_entries`, `gravityforms_view_entry_notes`, `gravityforms_edit_entry_notes` (`modules/class-gf-module.php:165-215`). By default Gravity Forms grants these to Administrator only; whether an Editor has them depends on the site's Members/role configuration.
- Descriptor abilities with no explicit map fall back to `manage_options` (`classes/trait-descriptor-abilities.php:181-182`).

The MCP tool names seen on live sites (`restlesswp-list-posts`, `restlesswp-get-post-revision`, …) are not present in this 0.9.11 checkout; [#3](https://github.com/alexmansfield/unhost/issues/3) owns the full tool → capability list. Whatever they proxy, core's post capability model in the table above applies underneath.

**Answer to brief open item 8.** An Editor credential is workable for day-to-day content work (posts, pages, media, taxonomy, comments, per-post ACF/Etch/SEO values) and is blocked from users, plugins, themes, settings, site health, and RestlessWP's schema/config modules. If the operator's day-to-day includes ACF/Etch schema edits, plugin toggles or settings, those calls need an Administrator credential — which is precisely the split the elevation design (#15) can exploit: the "open" tier fits inside Editor; the "dangerous" tier is what Administrator adds. Note that Editor still carries `unfiltered_html` on single-site installs (so Editor content writes can inject script) and full delete rights over all posts and pages, so Editor is not a read-mostly credential.

## 5. Revocation and invalidation

| Path | Mechanism | Effect | Source |
|---|---|---|---|
| Profile page, per password or "Revoke all" | `wp-admin/profile.php` → `wp-admin/js/application-passwords.js` calls `DELETE /wp/v2/users/{id}/application-passwords[/{uuid}]` with cookie+nonce auth | Immediate: the next Basic-auth request finds no matching hash | `user-edit.php:790-869`; `application-passwords.js:85-130` |
| REST, from any client holding a credential for that user, or an Administrator's for any user | same routes; `delete_items` → `delete_all_application_passwords`, `delete_item` → `delete_application_password`; each fires `wp_delete_application_password` | Immediate | controller `:392-411, 447-474`; class `:374-430` |
| WP-CLI, fleet-wide over hosting access | `wp user application-password delete <user> --all` or `<uuid>…`; `<user>` is login, email or ID; `list <user> --format=json` to audit first | Immediate; no web request required, works while the site is under attack | [delete](https://developer.wordpress.org/cli/commands/user/application-password/delete/), [list](https://developer.wordpress.org/cli/commands/user/application-password/list/) |
| Site-wide disable | `add_filter( 'wp_is_application_passwords_available', '__return_false' )` (mu-plugin) | Every app-password auth fails with `application_passwords_disabled`; stored passwords are **kept** and resume when the filter is removed; REST endpoints return 501 | `user.php:424-428, 5140-5149`; controller `:682-688` |
| Per-user disable | `wp_is_application_passwords_available_for_user` filter returning false | Same, for that user | `user.php:429-433, 5162-5184` |
| Delete the WordPress user | `wp_delete_user()` deletes all user meta on single site | Passwords gone with the user | `wp-admin/includes/user.php:440-448` |
| Change the user's role | writes `wp_capabilities` meta only | **Does not invalidate.** The credential keeps authenticating; capabilities are resolved per request from the current role, so a demotion to Subscriber takes effect on the next call, and a promotion likewise | `user.php:457-499` (no role check); grep shows `_application_passwords` is written only by `WP_Application_Passwords` |
| Change the user's login password, destroy sessions | `wp_set_password`, `wp_destroy_all_sessions` | **Does not invalidate.** App passwords are a separate meta row and are not sessions | grep of `wp-includes`/`wp-admin` for the meta key: only `class-wp-application-passwords.php` and the 5.6 upgrade routine |
| Deactivate or delete a plugin (RestlessWP, authwp, security plugins) | — | **Does not invalidate.** Core owns the credential. Deactivating RestlessWP removes its routes/tools but `/wp/v2/*` remains reachable with the same credential. Deactivating a plugin that filtered availability to `false` *re-enables* app passwords | `wp_is_application_passwords_available` is the only switch, `user.php:5140-5149` |
| Disable XML-RPC | `xmlrpc_enabled` filter / server block | Closes the second surface the credential is valid on | `user.php:387` |

**Runbook implications (for #16).** Because any credential can create more credentials for its own user and change that user's password and email (§2), "delete the one UUID the gateway knows" is insufficient after a compromise: revoke **all** passwords on the user (`--all` / collection `DELETE`), reset the user's password and check the email, and prefer the WP-CLI path, which does not depend on the gateway or on the credential still being valid. The gateway *can* revoke itself in the normal (non-incident) offboarding case: `GET .../me/application-passwords/introspect` → `DELETE .../me/application-passwords/{uuid}` — the introspect route is only answerable by the credential's own user (`:491-497`), so the gateway can only ever learn and delete its own UUID this way. Rotation is the same two calls after a `POST` that mints the replacement; the old and new passwords coexist until the delete.

Two hooks are useful on the WordPress side if a per-site plugin is ever in scope: `wp_create_application_password` / `wp_delete_application_password` (audit; `class-wp-application-passwords.php:150, 394, 423`) and `wp_authenticate_application_password_errors` (veto, e.g. an IP allow-list; `user.php:478`).

## 6. Multisite

- **Credential scope is the network.** `_application_passwords` is user meta, which is global in multisite; `wp_authenticate_application_password()` does not check blog membership. A credential authenticates on every site; what it can *do* on each site is that site's role for the user (possibly none). The REST app-password controller refuses to operate on a user who is not a member of the current site unless the user has `manage_sites` (`class-wp-rest-application-passwords-controller.php:722`).
- **`using_application_passwords` is a network option** (`class-wp-application-passwords.php:53-56, 119-122`).
- **Managing other users' passwords needs `manage_network_users`** (super admin); a site Administrator cannot list, create or delete another user's app passwords via REST on multisite (`capabilities.php:74-79`). Removing a user from one site (`remove_user_from_blog`) leaves the meta — and the credential — intact for the other sites (`wp-admin/includes/user.php:441-442`; `wp-includes/ms-functions.php:240`).
- **Super-admin-only capabilities** relevant to the gateway's dangerous tier: `install_plugins`, `update_plugins`, `delete_plugins`, `install_themes`, `update_themes`, `delete_themes`, `update_core`, `edit_files/edit_plugins/edit_themes`, `delete_user(s)`, `unfiltered_html`, and `create_users` unless the network sets `add_new_users` (`capabilities.php:594-603, 619-642, 673-690`). Plugin activation by a site Administrator additionally requires the network to expose the plugins menu, else `manage_network_plugins` (`:654-666`). The roles article summarises the same list under "Super Admin".
- **`unfiltered_html`** is stripped from Administrators and Editors on multisite (`capabilities.php:594-603`), which lowers the blast radius of an Editor credential there.
- **Deleting a user via `DELETE /wp/v2/users/{id}`** on multisite needs a super admin and only removes the user from the current site; the credential survives on the others.

## 7. Onboarding surface (context only, out of scope)

`wp-admin/authorize-application.php` takes `app_name` (required), `app_id`, `success_url`, `reject_url`; validation is `wp_is_authorize_application_password_request_valid()` (`wp-admin/includes/user.php:654-700`; `http` redirect URLs are only allowed for loopback/local since 6.3.2, `:713+`). On approval the site appends `site_url`, `user_login` and `password` to `success_url`. The REST index advertises the URL under `authentication["application-passwords"].endpoints.authorization` (`rest-api.php:1265-1277`). This is authwp's mechanism; the `wordpress` module only stores what comes out of it.

## 8. What this means for the tickets that depend on it

- **#12 (credentials, verification).** Verify with `GET /wp/v2/users/me?context=edit`; store `id`, `username`, `roles`; optionally `GET .../me/application-passwords/introspect` to record the credential's `uuid`, `name`, `created` and to show `last_used`/`last_ip` (day-granular) in the Sites UI. The gateway can rotate and self-revoke via REST.
- **#15 (elevation).** The Editor/Administrator boundary in §4 is a natural open/dangerous split: everything the "dangerous" tier adds (users, plugins, themes, settings, schema modules) is exactly what Editor cannot do, so a design that holds *two* credentials per site (Editor for open, Administrator for elevated) enforces the tier in WordPress rather than only in the gateway. Single-credential-with-Administrator relies entirely on the gateway's classifier.
- **#16 (security posture, revocation).** Correct the runbook: the gateway *can* revoke itself, but incident revocation must still be WP-side and must be `--all` plus a password reset on the user, because the leaked credential can mint siblings and change the account. XML-RPC is a second surface. `last_used` is throttled to daily, so it cannot serve as a live-activity signal.
- **#3 (RestlessWP).** RestlessWP's permission model is `current_user_can` per tool with per-controller read/write caps; the transport only requires a logged-in user. Whatever the catalogue lists as `manage_options` is Administrator-only.
